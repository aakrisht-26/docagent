## 1. Big Picture

DocAgent answers one question: **"What is in this document?"**

You give it a file (PDF, Excel, CSV, audio) or a YouTube URL. It gives you back a structured report: a summary, a list of questions or form fields, extracted tables, and full metadata — all generated by an LLM running on Groq Cloud.

Think of it as a document analyst pipeline that:

1. **Reads** the document — turns raw bytes into structured text
2. **Cleans** the text — fixes encoding, repairs hyphenation, normalises whitespace
3. **Classifies** it — is this a questionnaire/form or a normal document? What domain?
4. **Extracts structure** — pulls tables from complex domain documents using computer vision
5. **Summarises** it — map-reduce approach for long documents, extractive fallback without LLM
6. **Extracts questions** — three-layer extraction (regex + LLM + deduplication)

Every step is a separate, independently testable **skill**. The **agent** is just the coordinator that calls them in order.

### Why this split matters

If summarisation fails on a 200-page document, the pipeline doesn't crash — it returns a partial result with everything else intact, and the error is surfaced in `PipelineResult.errors`. You can fix the summariser, re-run only that step (in tests), and the rest of the system is unaffected.

## 2. Technology Stack — Library Decision Log

Every library in this project was chosen for a specific reason. This section documents those decisions so future engineers understand the constraints and can make informed choices if a library needs to be replaced.

### Python

**Version:** 3.11+. Reason: `match` statements (used in config parsing), improved `tomllib`, and significantly faster interpreter than 3.10 on CPU-bound text processing.

### LLM Provider — Groq Cloud

**Why Groq instead of OpenAI or Anthropic directly?**

Groq runs open-weight models (Llama 3.3 70B) on custom LPU (Language Processing Unit) hardware. The key property: **inference speed**. Groq returns tokens at 400–800 tokens/second vs 30–60 tokens/second from OpenAI GPT-4. For DocAgent's use case — processing a 100-page document through a map-reduce summarisation pipeline — this means 15 seconds instead of 4 minutes.

The second reason: **cost**. Groq's pricing for Llama 3.3 70B is roughly 10× cheaper per token than GPT-4 Turbo. Since DocAgent can send the same document text to the LLM dozens of times (once per chunk in map-reduce), cost compounds quickly.

The trade-off: Groq runs Llama, not GPT-4. For document summarisation and classification, Llama 3.3 70B is empirically equivalent for our tasks. For highly creative or highly ambiguous reasoning, GPT-4 would be better.

**Why Llama 3.3 70B specifically?**

We evaluated Llama 3.1 8B, 70B, and Mixtral 8x7B. 8B produces significantly worse summaries for technical documents — it tends to hallucinate entity names. Mixtral 8x7B is good but slower than Llama 3.3 70B on Groq's LPUs. 70B hits the right balance of quality, speed, and cost.

### OpenAI Python SDK (pointed at Groq)

**Why use the OpenAI SDK to call Groq?**

Groq exposes an OpenAI-compatible REST API. By using the OpenAI Python SDK with `base_url="https://api.groq.com/openai/v1"`, we get all of OpenAI's client-side benefits (retry logic, timeout handling, streaming) while calling Groq's infrastructure. This also means switching to actual OpenAI requires changing two lines — the `base_url` and the model name.

### PDF Parsing — pdfplumber (primary), PyMuPDF/fitz (fallback)

**Why pdfplumber as primary?**

pdfplumber is built on pdfminer.six and provides the highest-quality structured extraction from PDFs. Crucially, it provides **bounding boxes for both text blocks and tables**, enabling the table-masking technique that prevents duplicate content in mixed text/table PDFs (see §7.2). No other library gives you both at the layout level.

**Why PyMuPDF (fitz) as fallback?**

PyMuPDF is fast, handles encrypted PDFs that pdfplumber cannot, and is significantly more memory-efficient for large files. Its weakness: no structured table extraction. We use it as fallback precisely because the documents reaching this fallback tend to be difficult PDFs where structured extraction has already failed.

**Why not PyPDF2?**

PyPDF2 is deprecated (succeeded by pypdf). More importantly, it often produces garbled output on CJK characters, mathematical symbols, and ligatures — common in academic and technical PDFs. pdfplumber and PyMuPDF both handle these correctly.

**Why not PDFMiner directly?**

pdfplumber wraps PDFMiner and adds a much better API. Using PDFMiner directly is like using raw sockets instead of requests.

### OCR — Tesseract + OpenCV

**Why Tesseract over EasyOCR or PaddleOCR for the OCR fallback?**

Tesseract is the only major OCR engine with zero additional dependencies beyond a system binary install. EasyOCR requires PyTorch; PaddleOCR requires PaddlePaddle. These are 500 MB+ installs. Tesseract is 50 MB. For a fallback that handles scanned PDFs (a minority of inputs), the simpler dependency tree is the right choice.

**Why OpenCV for pre-processing?**

OpenCV's adaptive thresholding (`adaptiveThreshold`) handles uneven lighting in scanned documents better than any other approach. A document photographed under a lamp will have bright and dark regions — a global threshold binarises poorly in shadows. Adaptive thresholding picks a per-neighbourhood threshold. The Gaussian blur (`GaussianBlur`) before thresholding suppresses noise pixels that would otherwise become false text characters.

### Computer Vision Tables — PaddleOCR PP-Structure

**Why PP-Structure for table extraction in complex domains?**

pdfplumber detects tables by looking for PDF line drawing commands (vector graphics). Many professional documents — annual reports, academic papers, engineering specs — use tables that are *visually* obvious but have no underlying line rules in the PDF content stream. PP-Structure infers table structure from visual patterns: column alignment, row spacing, font consistency. It produces HTML table output that preserves merges, spans, and multi-level headers.

**Why not Camelot or Tabula?**

Camelot and Tabula both rely on PDF vector data (like pdfplumber) and fail for the same reason. They are excellent for simple tables in clean PDFs; for complex domain documents, they produce garbled output.

**Why is it lazy-loaded?**

PP-Structure downloads ~400 MB of model weights on first use and allocates GPU memory. Initialising it at `DocumentAgent.__init__` would add 3–10 seconds of startup time and VRAM allocation for every DocAgent instance, even when processing plain-text or audio documents that never need table extraction. Lazy loading means it only pays its cost when it's actually needed.

### Excel — openpyxl

**Why openpyxl over xlrd?**

xlrd dropped support for `.xlsx` files in v2.0 (security concerns with XML formula injection). openpyxl handles both `.xlsx` and modern Excel features (merged cells, named ranges). For reading values only (`data_only=True`), it's the industry standard.

### Audio Transcription — Groq Whisper via OpenAI SDK

**Why Groq Whisper instead of local Whisper (OpenAI open-source)?**

Local Whisper requires a GPU for reasonable performance (1× realtime on CPU for large model). Groq's Whisper endpoint runs on LPUs at roughly 50× realtime — a 5-minute video transcribes in under 10 seconds. The dependency cost of local Whisper (PyTorch, CUDA) vastly outweighs the benefit for a service that transcribes occasionally.

**Why MP3 format for audio downloads?**

Groq Whisper has a 25 MB file size limit. Uncompressed WAV at 44.1 kHz stereo = ~10 MB/minute. A 5-minute YouTube video becomes 50 MB — over the limit. MP3 at 128 kbps = ~1 MB/minute. The quality loss is inaudible to Whisper's neural acoustic model, which doesn't benefit from audio fidelity above ~16 kHz sample rate.

### YouTube Download — yt-dlp

**Why yt-dlp instead of pytube or youtube-dl?**

youtube-dl is effectively unmaintained (last significant update 2022). pytube breaks frequently on YouTube's anti-bot measures. yt-dlp is actively maintained, handles age-restricted content, Shorts, playlists, and is the de facto standard. It also supports a programmatic Python API, which we use as the primary path, with the CLI binary as fallback.

### Text Repair — ftfy

**Why ftfy for encoding repair?**

`ftfy` (Fix Text For You) specifically targets the most common real-world encoding corruption: Latin-1 bytes decoded as UTF-8, producing sequences like `Ã©` instead of `é`. This is extremely common in PDFs generated by older publishing tools (InDesign, QuarkXPress) on Windows machines. No other library specifically targets this class of corruption.

### UI Framework — Streamlit

See §12.1 for the detailed rationale. Short version: Streamlit is the right tool for single-developer AI application prototypes that need to ship quickly without a separate frontend team.

### PDF Export — ReportLab

**Why ReportLab over WeasyPrint or pdfkit?**

WeasyPrint requires a full HTML/CSS rendering engine and libcairo as a system dependency. pdfkit wraps wkhtmltopdf, which is an Electron-sized binary. ReportLab is a pure-Python library with no system dependencies. Since we're generating structured reports (not rendering arbitrary HTML), ReportLab's programmatic API is cleaner than either alternative.

### Testing — pytest

Standard choice. `pytest-mock` used for LLM call mocking. No additional test framework needed.

## 3. Architecture Pattern — Agent-Skill Separation

### The Core Principle

> **Agents orchestrate. Skills execute. They never mix.**

A **skill** is a pure function wrapped in a class. It:
- Takes a `SkillInput` (a typed dict wrapper)
- Does exactly one thing (parse a PDF, classify text, summarise)
- Returns a `SkillOutput` (success flag + data + error + timing)
- **Never** calls another skill
- **Never** holds inter-call state

An **agent** is a coordinator. It:
- Knows which skills to call and in what order
- Passes the output of one skill as input to the next
- Collects errors and warnings
- Returns a `PipelineResult` — the final typed report

### Why this separation is not just style

The separation provides three concrete engineering benefits:

**1. Independent testability.** You can unit-test `SummarizationSkill` by constructing a `SkillInput(data={"full_text": "...", "doc_type": "normal_document"})` directly — no file system, no pipeline, no mocks of other skills. This makes tests fast and precise.

**2. Failure isolation.** When a skill fails, `safe_execute()` catches the exception and returns `SkillOutput(success=False, error=str(exc))`. The agent checks this, logs it, and continues to the next step. A bug in table extraction doesn't prevent summarisation.

**3. Zero-config extensibility.** The `SkillRegistry` auto-discovers all `BaseSkill` subclasses on startup (see §6). Adding a new skill requires creating one file — nothing else changes.

### Why not use a pipeline framework like LangChain or LlamaIndex?

LangChain and LlamaIndex are designed for LLM-native pipelines where every step is an LLM call. DocAgent's pipeline mixes heavy PDF parsing (CPU/IO-bound), computer vision (GPU-bound), LLM calls (network-bound), and pure text processing (CPU-bound). A generic LLM pipeline framework adds abstractions that don't fit this mixed workload and makes it harder to reason about step-by-step failures.

More practically: LangChain's API changes significantly between minor versions. For a production system, direct orchestration code that we control is more reliable than taking an upstream dependency on a fast-moving framework.

### The call graph

```
UI (Streamlit)
    │
    ▼
DocumentAgent.run(file_path)  ──or──  DocumentAgent.run_youtube(url)
    │
    ├─► Step 1: Parse
    │       PDFReaderSkill / ExcelReaderSkill / AudioReaderSkill
    │       → ParsedDocument (chunks, tables, full_text, metadata)
    │
    ├─► Step 2: Clean
    │       TextCleanerSkill
    │       → ParsedDocument (encoding fixed, noise removed)
    │
    ├─► Step 3: Classify
    │       DocumentClassifierSkill
    │       → ClassificationResult (doc_type, domain, confidence)
    │
    ├─► Step 3.5: Structure Recognition  [planner-gated, Technical/Financial only]
    │       StructureRecognitionSkill
    │       → ParsedDocument (tables enriched with HTML)
    │
    ├─► Step 4: Summarise  [planner-gated]
    │       SummarizationSkill
    │       → {summary: str, citations: List[Dict]}
    │
    ├─► Step 5: Extract Questions  [planner-gated]
    │       QuestionExtractionSkill
    │       → {questions: List[str]}
    │
    └─► Step 6: Assemble
            Builds PipelineResult from all outputs
```

### Planner-gating: why not run every skill every time?

Some skills are expensive. `StructureRecognitionSkill` can take 5–15 minutes on CPU for a complex document. `SummarizationSkill` makes multiple LLM calls that cost money and API quota. Running them on a 2-page CSV file would be wasteful and slow.

`PipelinePlanner.plan(doc_stats)` decides which steps to run based on the document's characteristics:

```python
@dataclass
class DocStats:
    file_type: str        # "pdf" | "excel" | "audio"
    word_count: int
    page_count: int
    doc_type: str         # from classification
    domain: str           # from classification

def plan(stats: DocStats) -> PipelineFlags:
    return PipelineFlags(
        run_structure  = stats.domain in TARGET_DOMAINS and stats.file_type == "pdf",
        run_summarize  = stats.word_count > 50,
        run_questions  = stats.doc_type == "questionnaire" or stats.word_count > 200,
    )
```

This is not AI-driven planning. It's deterministic business logic. That's intentional: predictable, testable, and fast.

## 4. Data Models — The Typed Contract

All inter-component data flows through typed dataclasses in `core/models.py`. This is not optional styling — it is the contract that makes skills independently testable and the pipeline composable.

### Why dataclasses instead of Pydantic?

Pydantic adds runtime validation and JSON serialisation, which is useful for API endpoints receiving external data. Inside DocAgent, all data is internal — created by our own code, passed between our own functions. The overhead of Pydantic's validators on every object creation adds up in a tight loop (e.g., creating thousands of `DocumentChunk` objects when parsing a 200-page PDF). Python dataclasses give type safety at development time (via mypy) with zero runtime overhead.

### DocumentChunk

```python
@dataclass
class DocumentChunk:
    text: str               # The actual text content
    page_or_sheet: int|str  # Page number (int) for PDF, sheet name (str) for Excel
    chunk_index: int        # 0-based position in the document
    metadata: Dict[str, Any]
```

**What it represents:** A single content unit — one page of a PDF, or one sheet of an Excel file. For very long pages, `TextCleanerSkill` can further split a chunk.

**Why `page_or_sheet` is a union type:** PDFs use integer page numbers; Excel uses string sheet names. Downstream skills that need to cite sources (summarisation, chat) use this field in their output. Keeping it as `int|str` preserves the original document's reference system rather than imposing a artificial normalisation.

### ParsedDocument

```python
@dataclass
class ParsedDocument:
    file_name: str
    file_type: str          # "pdf" | "excel" | "audio"
    chunks: List[DocumentChunk]
    full_text: str          # chunks concatenated — the primary input for all LLM skills
    tables: List[Dict[str, Any]]
    metadata: Dict[str, Any]
    page_count: int
    sheet_names: List[str]
```

**Key properties:**
- `is_empty` → `full_text.strip() == ""` — used by the agent to abort early
- `word_count` → `len(full_text.split())`
- `char_count` → `len(full_text)`

**Why store both `chunks` and `full_text`?**

`full_text` is the concatenation of all chunk texts — used when a skill needs the entire document as one string (classification, short-document summarisation). `chunks` is used when a skill needs to know *which page* a piece of text came from (citation generation, table extraction). Storing both avoids repeated concatenation/splitting.

### SkillInput / SkillOutput

Every skill's public API uses exactly these two types:

```python
@dataclass
class SkillInput:
    data: Dict[str, Any]       # Skill-specific payload
    metadata: Dict[str, Any]   # Request-level context (defaults to {})

@dataclass
class SkillOutput:
    success: bool
    data: Any                  # Skill-specific result
    error: Optional[str]       # Non-None only on failure
    warnings: List[str]        # Non-fatal issues (document truncated, OCR quality low, etc.)
    metadata: Dict[str, Any]
    duration_ms: float         # Execution time, filled automatically by safe_execute
```

**Why not type the `data` field more specifically?**

Each skill returns a different shape of data. `PDFReaderSkill` returns a `ParsedDocument`; `SummarizationSkill` returns `{"summary": str, "citations": List[Dict]}`. Typing `data: Any` and documenting the expected shape per-skill is more practical than a deeply nested generic type hierarchy. The alternative — a separate result dataclass per skill — would require every agent call-site to import and handle 12 different result types.

### ClassificationResult

```python
@dataclass
class ClassificationResult:
    doc_type: str          # "questionnaire" | "normal_document"
    domain: str            # "Technical" | "Financial" | "General" | "Medical" | ...
    confidence: float      # 0.0 – 1.0
    method: str            # "heuristic" | "llm" | "hybrid"
    signals: Dict[str, Any]  # Which patterns matched, for debugging
```

`domain` is the most architecturally important field. It gates `StructureRecognitionSkill` (only Technical/Financial/Research/Scientific), shapes the summarisation persona ("You are a Senior Financial Analyst" vs "You are a Technical Documentation Specialist"), and influences question extraction's few-shot examples.

## 5. The Pipeline — Step by Step

`DocumentAgent.run(file_path)` is the main entry point for file-based processing. `DocumentAgent.run_youtube(url)` handles YouTube, but both converge into `_run_core_pipeline()` — the shared Steps 2–6.

### Step 0: Validate

```python
ext = file_path.suffix.lower()
if ext not in SUPPORTED_EXTENSIONS:
    return self._error_result(file_path, "Unsupported file type")
file_type = SUPPORTED_EXTENSIONS[ext]  # "pdf" | "excel" | "audio"
```

`SUPPORTED_EXTENSIONS` maps extensions to type strings. Adding a new format is one line here, one line in `file_handler.py`, and one line in `app.py`'s file uploader.

### Step 1: Parse

```python
if file_type == "pdf":
    reader = self._pdf_reader
elif file_type == "audio":
    reader = self._audio_reader
else:
    reader = self._xls_reader

parse_out = reader.safe_execute(SkillInput(data={"file_path": str(file_path)}))
```

All three readers return a `ParsedDocument`. This is the architecture's most important abstraction — it means the LLM never knows whether it's reading a transcript, a spreadsheet, or a PDF. The downstream skills are format-agnostic.

**If parsing fails** or the document is empty: the pipeline aborts with an error `PipelineResult`. Nothing downstream runs.

### Step 2: Clean

```python
clean_out = self._cleaner.safe_execute(SkillInput(data={"parsed_document": parsed_doc}))
if clean_out.success and clean_out.data:
    parsed_doc = clean_out.data  # Replace with cleaned version
full_text = parsed_doc.full_text
```

Note the guard: `if clean_out.success and clean_out.data`. Cleaning is *non-fatal*. If the cleaner crashes on a malformed document, the agent falls back to the raw parsed text and continues. This is the error handling philosophy throughout the pipeline: each step is best-effort, and failures degrade gracefully rather than abort.

### Step 3: Classify

```python
classify_out = self._classifier.safe_execute(SkillInput(data={"full_text": full_text}))
class_result = classify_out.data if classify_out.success else None
doc_type  = class_result.doc_type if class_result else "normal_document"
domain    = class_result.domain   if class_result else "General"
```

If the LLM is unavailable, the heuristic phase still runs and produces a classification. If even that fails, defaults are used and the pipeline continues. Classification failure never stops document processing.

### Step 3.5: Structure Recognition (Planner-gated)

```python
if plan.run_structure:
    struct_out = self._struct_rec.safe_execute(SkillInput(data={
        "parsed_document": parsed_doc,
        "file_path": str(file_path),
        "domain": domain
    }))
    if struct_out.success and struct_out.data:
        parsed_doc = struct_out.data
        full_text = parsed_doc.full_text  # Updated with table HTML embedded
```

When PP-Structure succeeds, it mutates `full_text` to include `[TABLE_HTML]...[/TABLE_HTML]` blocks. The LLM summariser understands these blocks and incorporates the table data into the summary.

### Steps 4 & 5: Summarise and Extract Questions

Both follow the same call-and-check pattern. Failures produce empty outputs, not crashes.

```python
summ_out = self._summarizer.safe_execute(SkillInput(data={
    "full_text":     full_text,
    "doc_type":      doc_type,
    "domain":        domain,
    "parsed_document": parsed_doc,
    "summary_length":  summ_cfg.get("summary_length", "Standard"),
    "summary_tone":    summ_cfg.get("summary_tone", "Professional"),
}))
summary  = summ_out.data.get("summary", "")   if (summ_out.success and summ_out.data) else ""
citations = summ_out.data.get("citations", []) if (summ_out.success and summ_out.data) else []
```

### Step 6: Assemble

```python
return PipelineResult(
    file_name   = file_path.name,
    file_type   = file_type,
    doc_type    = doc_type,
    domain      = domain,
    summary     = summary,
    questions   = questions,
    tables      = parsed_doc.tables,
    raw_text    = full_text,
    errors      = errors,
    warnings    = warnings,
    skill_timings = self._timings,
    success     = len(errors) == 0,
)
```

`success=True` means no *fatal* errors. Partial results (summarisation failed but classification succeeded) have `success=True` with populated `warnings` and an empty `summary`. The UI displays warnings in a banner above the results.

## 6. Skill Registry — Auto-Discovery

`core/skill_registry.py` implements a singleton that auto-discovers all `BaseSkill` subclasses at import time. No registration step is required anywhere.

### How discovery works

```python
import pkgutil, importlib, inspect
for _finder, module_name, _ispkg in pkgutil.iter_modules(skills.__path__):
    if module_name == "base_skill":
        continue
    module = importlib.import_module(f"skills.{module_name}")
    for name, obj in inspect.getmembers(module, inspect.isclass):
        if issubclass(obj, BaseSkill) and obj is not BaseSkill and obj.name:
            self._skills[obj.name] = obj
```

It walks the `skills/` package, imports each module, finds all concrete `BaseSkill` subclasses (those with a non-empty `name` attribute), and registers them. Adding a new skill to `skills/` automatically makes it available everywhere.

### Why a singleton?

The registry builds its map by importing every skill module. This is not free — it involves filesystem access and module execution. A singleton ensures this cost is paid once at startup, not once per call. `reset()` is provided for tests that need a clean slate between test cases.

```python
class SkillRegistry:
    _instance = None

    def __new__(cls):
        if cls._instance is None:
            cls._instance = super().__new__(cls)
            cls._instance._skills = {}
        return cls._instance
```

### Why not a decorator-based registry?

The alternative is `@register_skill` decorators on each class. This requires every skill module to import the registry, creating a circular dependency (registry imports skills; skills import registry). The `pkgutil` discovery approach keeps skills completely decoupled from the registry infrastructure.

## 7. Skills Deep Dive

### 7.1 BaseSkill

`skills/base_skill.py` defines the interface every skill must implement.

The key method is `safe_execute()`, which is a **template method** — it wraps `execute()` with input validation, timing, and exception handling:

```python
def safe_execute(self, inputs: SkillInput) -> SkillOutput:
    error = self.validate_inputs(inputs)    # Check required_inputs list
    if error:
        return SkillOutput(success=False, data=None, error=error)

    start = time.monotonic()
    try:
        result = self.execute(inputs)
        if result.duration_ms == 0.0:
            result.duration_ms = (time.monotonic() - start) * 1000
        return result
    except Exception as exc:
        duration_ms = (time.monotonic() - start) * 1000
        return SkillOutput(success=False, data=None, error=str(exc), duration_ms=duration_ms)
```

**Why does `safe_execute` time the execution even if `execute` sets it?**

Some skills perform their own timing for internal sub-step breakdowns. `safe_execute` only fills `duration_ms` if it's still 0 after `execute` returns. This allows skills to report fine-grained timings internally while still being covered by the outer timer as a fallback.

**You always call `safe_execute()`, never `execute()` directly** (except in unit tests targeting the raw execute logic).

### 7.2 PDFReaderSkill

**Location:** `skills/pdf_reader_skill.py`
**Purpose:** Turn a PDF file path into a `ParsedDocument`.

This skill runs a three-engine fallback chain designed to handle the enormous variety of PDFs in the real world.

#### Engine 1: pdfplumber (primary)

```python
with pdfplumber.open(file_path) as pdf:
    for page in pdf.pages[:self._max_pages]:
        # Step 1: Extract tables as structured objects
        tables = page.extract_tables()
        table_bboxes = [t.bbox for t in page.find_tables()]
        # Step 2: Mask table areas from text extraction
        masked_page = page
        for bbox in table_bboxes:
            masked_page = masked_page.outside_bbox(bbox)
        # Step 3: Extract text from non-table areas only
        text = masked_page.extract_text(layout=True)
```

**The table-masking technique** is the core insight here. PDFs encode content in two ways:
1. As text characters with positions in the content stream (readable as text)
2. As visual drawing commands that create the *appearance* of a table

A typical financial PDF renders a table by drawing rectangles (the cells) AND placing text characters inside those rectangles. If you extract text naively, you get the table content twice: once from the text stream (as a block of numbers), and once from pdfplumber's table parser (as a structured grid). The table-masking approach solves this by:
1. Extracting the table boundaries as bounding boxes
2. Masking (cropping out) those bounding boxes before text extraction
3. Handling tables and text as completely separate extractions

Without table masking, a financial report's income statement would appear as both a formatted table in `parsed_doc.tables` and as a jumble of duplicate numbers in `full_text`, corrupting the LLM's input.

#### Engine 2: PyMuPDF (fallback)

```python
doc = fitz.open(str(file_path))
for page in doc:
    text = page.get_text("text")
```

Simple, fast, no table extraction. Triggered when pdfplumber fails (encrypted PDFs, complex vector graphics, password-protected documents that pdfplumber can't parse). PyMuPDF handles a broader range of PDF corruptions because it uses MuPDF, one of the most battle-hardened PDF rendering engines.

#### Engine 3: Tesseract OCR (final fallback)

Only triggered when both text engines return empty or garbage content:

```python
def _is_garbage_text(text: str) -> bool:
    words = text.split()
    if len(words) < 5:
        return True
    # Check ratio of words containing only non-alphabetic characters
    garbage_words = sum(1 for w in words if not any(c.isalpha() for c in w))
    return garbage_words / len(words) > 0.6
```

The OCR pipeline for each page:
1. Render to 400 DPI image via PyMuPDF (higher DPI = more pixels per character = better OCR)
2. Convert to grayscale
3. Apply Gaussian blur (5×5 kernel) — reduces salt-and-pepper noise from scanner sensors
4. Apply adaptive thresholding — normalises contrast across uneven lighting
5. Deskew: find the largest text contour, rotate to align with horizontal axis
6. Pass to Tesseract with `--psm 3` (automatic page segmentation) and `--oem 3` (LSTM neural net)

**Why 400 DPI specifically?** Tesseract's accuracy drops noticeably below 300 DPI for small fonts (8pt and below). 300 DPI is sufficient for standard text; 400 DPI provides margin for small-print legal text and footnotes. Going higher (600 DPI) produces diminishing accuracy returns while quadrupling memory usage.

### 7.3 ExcelReaderSkill

**Location:** `skills/excel_reader_skill.py`
**Purpose:** Turn Excel (.xlsx, .xls) or CSV into a `ParsedDocument`.

```python
wb = openpyxl.load_workbook(file_path, data_only=True)  # data_only ignores formulas
for ws in wb.worksheets[:self._max_sheets]:
    rows = []
    for row in ws.iter_rows(values_only=True):
        row_vals = [str(c).strip() for c in row if c is not None]

            rows.append(row_vals)
    df = self._rows_to_dataframe(rows)
    text = self._dataframe_to_text(df, ws.title)
```

**Why `data_only=True`?**

openpyxl can load workbooks in two modes: with or without formulas. With formulas, cells like `=SUM(B2:B10)` return the formula string, not the computed value. We want the computed value (what a human reading the spreadsheet would see). `data_only=True` returns cached values computed by Excel the last time the file was saved.

**Smart sampling for large sheets:**

```python
def _dataframe_to_text(self, df, sheet_name: str) -> str:
    if len(df) > 600:
        head = df.head(300).to_string(index=False, max_cols=30)
        tail = df.tail(300).to_string(index=False, max_cols=30)
        return f"{head}\n\n... [{len(df) - 600} rows omitted] ...\n\n{tail}"
    return df.to_string(index=False, max_cols=30)
```

A 10,000-row sales database would overflow the LLM's context window and waste significant API quota summarising rows that are structurally identical. The head+tail approach captures: (1) column headers in the first rows, (2) the data pattern in early rows, (3) how the data ends. The omitted row count tells the LLM the true scale of the dataset so it doesn't claim "this is a small dataset."

**CSV encoding chain:**

```python
for encoding in ["utf-8", "latin-1", "cp1252"]:
    try:
        df = pd.read_csv(file_path, encoding=encoding, ...)
        break
    except (UnicodeDecodeError, Exception):
        continue
```

Windows Excel exports CSV in cp1252 (Windows-1252) by default. Linux/Mac tools produce UTF-8. Latin-1 covers Western European diacritics. The three-encoding chain handles 99%+ of real-world CSV files without requiring the user to specify encoding.

### 7.5 TextCleanerSkill

**Location:** `skills/text_cleaner_skill.py`
**Purpose:** Normalise raw extracted text without destroying structural information needed by downstream skills.

The central challenge: **don't break headings**. The summariser uses headings for section-aware chunking. A naive noise filter would remove a line like `1.2 REVENUE ANALYSIS` because it's short, all-caps, and has no sentence-ending punctuation — all heuristics for "noise line". But it's a critical heading.

**The heading guard:**

```python
_HEADING_GUARD = re.compile(
    r"(?:^#{1,4}\s.+$"                           # Markdown headings
    r"|^\d+(?:\.\d+)*\s+[A-Z][^\n]{2,}$"         # Numbered: "1.2 Revenue"
    r"|^[A-Z][A-Z\s\-:]{4,}[A-Z]$)",             # ALL-CAPS: "EXECUTIVE SUMMARY"
    re.MULTILINE
)
```

Any line matching this guard is exempt from ALL cleaning rules that might remove it. The guard runs first on every cleaning step.

**Cleaning pipeline (in order):**
1. `ftfy.fix_text(text)` — repairs mojibake (`Ã©` → `é`, `â€™` → `'`)
2. Line ending normalisation: `\r\n` → `\n`
3. **PDF hyphenation repair**: `word-\nbreak` → `wordbreak` — PDFs often soft-hyphenate at line boundaries; this restores the original word
4. Page number removal: `^\s*(?:page\s*\d+|\d+\s*/\s*\d+)\s*$` — but NOT if it matches the heading guard
5. Lone bullet removal: `^[ \t]*[-•◦▪·][ \t]*$` — bullet character with no text
6. Collapse 3+ blank lines → 2 blank lines (preserve paragraph structure)
7. Strip trailing whitespace per line

**Why does hyphenation repair come before heading detection?** A heading could be split across a line break in the PDF's content stream as `REVENUE-\nANALYSIS`. Repairing it first ensures the heading guard sees `REVENUE-ANALYSIS` (still recognisable) rather than `REVENUE-` + `ANALYSIS` (two non-heading lines).

### 7.6 DocumentClassifierSkill

**Location:** `skills/document_classifier_skill.py`
**Purpose:** Determine document type (questionnaire vs normal) and domain (Technical, Financial, Medical, etc.).

#### Phase 1: Heuristic Scoring

Twenty compiled regex patterns, each with a weight:

| Pattern | Example match | Weight |
|---|---|---|
| Form title | "Customer Satisfaction Survey" | 0.20 |
| Q-numbering | "Q1.", "Question 2:" | 0.15 |
| Likert scale | "Strongly agree … Strongly disagree" | 0.15 |
| Rating scale | "On a scale of 1–10" | 0.12 |
| Multiple choice | "Select all that apply" | 0.12 |
| ABCD options | "(a) Yes  (b) No  (c) Maybe" | 0.10 |
| Form fields | "First Name: _____ Last Name: _____" | 0.08 |
| Checkbox glyphs | `☐ ☑ [ ] [x]` | 0.07 |
| Consent language | "I consent to…", "I declare that…" | 0.06 |
| Yes/No pairs | "Yes / No" on a single line | 0.06 |

Scores are summed and compared to `questionnaire_threshold` (default 0.4). Above 0.7: definitely a questionnaire (no LLM needed). Below 0.1: definitely a normal document (no LLM needed). Between 0.1–0.7: ambiguous, call LLM.

#### Phase 2: LLM Disambiguation (Borderline Only)

```python
prompt = f"""Classify the document excerpt as questionnaire or normal_document.
Return valid JSON only: {{"type": "...", "confidence": 0.95, "domain": "Technical"}}

Excerpt:
{text[:3000]}"""
```

The LLM confidence is blended with the heuristic: `0.7 * llm_conf + 0.3 * heuristic_score`. The 70/30 split favours the LLM (more context-aware) while keeping the heuristic as a stabilising prior (prevents wild swings from a single ambiguous LLM response).

**Why not always use the LLM?** Speed and cost. A document with "Customer Satisfaction Survey" in the title and 15 Likert items has a heuristic score of ~0.85 — obviously a questionnaire. The LLM call would add 2–5 seconds and use API quota to confirm what we already know with high certainty.

**Why only 3000 chars for the LLM excerpt?** Classification quality plateaus after the first ~2000 characters. The document type is established by its title, opening section, and structural patterns — all apparent in the first few pages. Sending the entire 50,000-character document burns tokens without improving accuracy.

#### Phase 3: Domain Detection

Always runs if LLM is available:

```python
domain_prompt = f"""Classify this document's domain. Choose ONE from:
Technical, Financial, Legal, Medical, Educational, Research, Scientific,
Government, HR/Administrative, General.

Document title/opening: {text[:1500]}

Return JSON: {{"domain": "...", "confidence": 0.9}}"""
```

Domain detection uses only 1500 characters because the domain is almost always apparent from the title and opening paragraph. Running it on the full document would be wasteful.

### 7.7 StructureRecognitionSkill

**Location:** `skills/structure_recognition_skill.py`
**Purpose:** Extract high-fidelity tables from complex domain documents using computer vision.

Only activates for Technical, Financial, Research, and Scientific domains — the domains where structured tables are both common and semantically important.

#### Why Computer Vision for Tables?

pdfplumber detects tables by looking for explicit line-drawing commands in the PDF vector data. This works for simple tables in reports generated by modern word processors.

Many real-world technical and financial documents have tables that are *visually* clear but have no explicit PDF line rules:
- Tables in scanned PDFs (image-only, no vector data)
- Tables in annual reports generated from InDesign layouts
- Complex academic paper tables with merged cells and multi-level headers
- Tables where cells are separated by whitespace alignment, not drawn lines

PP-Structure (PP-StructureV3 from PaddleOCR) is trained to infer table structure from *visual patterns*: column alignment, row height consistency, font similarity within rows, header styling. It produces HTML output with `<table>`, `<tr>`, `<td>` elements that capture row/column/merge structure accurately.

#### Lazy Loading Pattern

```python
def _get_engine(self):
    if self._engine is None:
        os.environ["PADDLE_PDX_DISABLE_MODEL_SOURCE_CHECK"] = "True"
        self._engine = PPStructureV3(lang="en", use_gpu=self._use_gpu, show_log=False)
    return self._engine
```

PP-Structure downloads ~400 MB of weights on first use and allocates significant GPU or CPU memory. Initialising it at startup would add 10–30 seconds of startup time for every DocAgent instance, even ones processing plain-text documents. The lazy pattern amortises this cost only to the documents that actually trigger it.

**`PADDLE_PDX_DISABLE_MODEL_SOURCE_CHECK=True`:** PaddleOCR's newer versions perform an internet check against Baidu's servers to verify model integrity before loading. This fails in air-gapped environments and adds 2–5 seconds of latency even when it succeeds. The flag disables this check.

### 7.8 SummarizationSkill

**Location:** `skills/summarization_skill.py`
**Purpose:** Generate a structured, domain-aware Markdown summary with inline page citations.

#### Scenario A: Short Document (Single Chunk)

The full text fits in the LLM's context window (~25,000 tokens for Llama 3.3 70B on Groq). One LLM call:

```
[System] You are a Senior {domain} Analyst. Write for a {tone} audience.
[User] Document content: {full_text}
Pages reference: {page_map}
Sections detected: {sections}

Task: Produce a {length} structured Markdown summary.
- Use ## headings for major sections
- Use ### for subsections
- Include inline citations [Source: Pages X, Y] after key facts
- Be factually precise — no hallucination
```

**Why inline citations?** Citations serve two purposes: (1) they let the reader verify facts against the original document, (2) they are parsed post-generation into structured `summary_citations` objects that downstream features (the chat tab, the UI's citation index) can use for navigation.

#### Scenario B: Long Document (Map-Reduce)

The document is split into section-aware chunks, each processed by the LLM independently (map), then synthesised (reduce):

**Map prompt** (per chunk, `temperature=0.1` for consistency):
```
You are a {domain} analyst extracting key information.
From this section, extract:
- Key entities (names, organisations, products, locations)
- Critical figures and percentages with their context
- Important dates and deadlines
- Regulatory or compliance points
Return concise bullet points only. No narrative.
```

**Reduce prompt** (all bullet points → final report):
```
You are synthesising {n} section analyses into a premium {tone} report.
Source sections: {all_bullets}

Instructions:
- Merge overlapping points, never duplicate
- Cover ALL entities, ALL figures, ALL dates mentioned
- Use ## headings for each major theme
- Cite pages: [Source: Pages X, Y]
- Length target: {length_instruction}
```

**Why not send the whole document in one reduce call?** Token cost and context window. A 100-page technical report might be 150,000 tokens. Llama 3.3 70B supports 128K context, but sending 150K tokens in one call would cost ~$0.15 per document and take 45+ seconds. The map phase compresses each section into ~200 tokens of bullet points. The reduce call sees ~5,000 tokens instead of 150,000 — 30× cheaper and faster.

**Why `temperature=0.1` for map, not 0.0?** Temperature 0.0 produces fully deterministic output but can cause the model to fixate on a single phrasing pattern. Temperature 0.1 introduces minimal variation that prevents repetitive bullet structures across chunks while maintaining factual precision. The reduce step uses `temperature=0.15` for slightly more natural prose.

#### Scenario C: LLM Unavailable (Extractive Fallback)

TF-IDF-like scoring without a vocabulary corpus:

```python
def _top_sentences(self, text, n):
    words = self._tokenize(text)         # Remove stopwords, stem basic plurals
    freq  = Counter(words)
    total = len(words)

    scored = []
    for i, sentence in enumerate(sentences):
        tokens = self._tokenize(sentence)
        if not tokens:
            continue
        score = sum(freq[w] / total for w in tokens) / len(tokens)
        # Position bonus: first/last 10% of document score 1.2×
        # (introductions and conclusions are information-dense)
        pos_ratio = i / max(len(sentences), 1)
        if pos_ratio < 0.1 or pos_ratio > 0.9:
            score *= 1.2
        # Length bonus: 40–200 char sentences are "just right" for summaries
        if 40 <= len(sentence) <= 200:
            score *= 1.1
        scored.append((score, sentence))
    return [s for _, s in sorted(scored, reverse=True)[:n]]
```

**Why not pure TF-IDF?** True TF-IDF requires a corpus of documents to compute IDF (inverse document frequency). We don't have a document corpus at inference time. Term frequency within the single document (normalised by document length) captures the same intent: words that appear often relative to document length are likely the document's key topics.

#### Section-Aware Chunking

Before map-reduce, the document is split at section boundaries rather than at fixed token counts:

```python
HEADING_PATTERNS = [
    re.compile(r'^#{1,4}\s+', re.MULTILINE),         # Markdown ## headings
    re.compile(r'^\d+(?:\.\d+)*\s{1,4}[A-Z]'),       # 1.2 Section Title
    re.compile(r'^[A-Z][A-Z0-9\s\-:]{4,}[A-Z]$'),    # ALL-CAPS TITLE
    re.compile(r'^.+\n[=\-]{4,}$', re.MULTILINE),    # Underlined Title
    re.compile(r'^(?:Section|Chapter|Part)\s+\d+'),   # Section 3
]
```

A section is kept together in one chunk unless it exceeds 1.5× the target chunk size. **Why 1.5× not 1×?** A section that's 110% of the target size is better sent as one unit than split mid-argument. Splitting a coherent argument between two map calls means the reduce step has to stitch it back together — it often can't, producing a summary that repeats the same point or misses the conclusion of an argument that started in one chunk and ended in another.

### 7.9 QuestionExtractionSkill

**Location:** `skills/question_extraction_skill.py`
**Purpose:** Extract all questions, form fields, and assessment items from a questionnaire.

#### Three-Layer Extraction

**Layer 1: Regex (always runs, zero API cost)**

Twelve compiled patterns targeting different question styles:

```python
# Numbered questions ending in ?
r"^\s*(?:\d{1,3}[\.\)])\s+([A-Z][^\n]{8,200}\?)"

# Q. prefix style
r"^[ \t]*(?:q(?:uestion)?[\s\.\-]*\d+)\s*[:\.\-]?\s*(.{5,200})$"

# Fill-in-the-blank (implicit questions)
r"(.{10,150}?)[:\s]+_{3,}"

# Likert scale header (question followed by scale options on next line)
r"^[ \t]*(.{10,200}?)\s*\n[ \t]*(?:strongly\s+agree|very\s+satisfied|..."
```

**Layer 2: LLM windows (better at implicit and multi-line questions)**

The document is split into 5,000-char windows with 200-char overlap (prevents questions spanning window boundaries from being missed):

```python
system = """You are a document analyst. Extract ALL questions, form fields,
and assessment items verbatim. Return ONLY valid JSON:
{"questions": ["Q1 text...", "Q2 text..."]}
If none found: {"questions": []}"""
```

`temperature=0.0` for deterministic, reproducible extraction. The LLM excels at implicit questions ("Describe your experience with our product") and multi-line questions that span paragraph breaks — both of which regex patterns struggle with.

**Layer 3: Post-processing**

```python
def _deduplicate(self, questions):
    seen = []
    for q in questions:
        tokens = set(q.lower().strip("?.").split())
        best = max(seen, key=lambda s: jaccard(tokens, s[0]), default=None)
        if best and jaccard(tokens, best[0]) >= 0.72:
            # Near-duplicate: keep the longer (more complete) version
            if len(q) > len(best[1]):
                seen.remove(best)
                seen.append((tokens, q))
        else:
            seen.append((tokens, q))
```

**Why Jaccard similarity for deduplication?**

Jaccard measures token set overlap: `|intersection| / |union|`. Example:
- "What is your age?" → `{what, your, age}`
- "Please enter your age in years" → `{please, enter, your, age, in, years}`
- Intersection: `{your, age}` (2 tokens)
- Union: 7 tokens
- Jaccard: 2/7 = 0.29 → **not duplicates** ✓

The threshold 0.72 was calibrated empirically on a corpus of real questionnaires. Below 0.72, false positives (erroneously merged distinct questions) became common. Above 0.80, false negatives (failing to catch near-duplicates from regex + LLM both extracting the same question) increased.

**Why keep the longer version when deduplicating?** Regex often captures a question by its first few words. The LLM usually captures the full question text including context. Keeping the longer version preserves the complete question as it appeared in the document.

### 7.10 DocumentChatSkill

**Location:** `skills/document_chat_skill.py`
**Purpose:** Multi-turn Q&A over the document without a vector database.

#### Embedding Retrieval, with Keyword Overlap as Fallback

> **This section previously argued for keyword overlap over embeddings, on three
> grounds that were later measured and found wrong.** The original text is
> preserved below under "The superseded argument", because the *shape* of the
> reasoning was sound — it was the numbers that were guessed rather than
> measured.

```python
def score_chunks(self, query, chunks) -> tuple[list[float], str]:
    # Preferred: cosine similarity over local embeddings.
    if embeddings.is_supported():
        cached = [c.get("embedding") for c in chunks]        # from DocumentStore
        matrix = np.asarray(cached) if all(v is not None for v in cached) \
                 else embeddings.encode([c["text"] for c in chunks])
        if matrix is not None:
            qv = embeddings.encode([query])
            if qv is not None:
                return list(embeddings.similarity(qv[0], matrix)), "embedding"

    # Fallback: keyword overlap, whenever the model is unavailable.
    qw = self._tokenize(query)
    return [float(len(qw & self._tokenize(c["text"]))) for c in chunks], "keyword_overlap"
```

`_select_chunks()` then takes the top 3 by score, appends the first/last
**anchors**, and caps at `_MAX_CONTEXT_CHARS`. **Only the scoring changed** —
the selection shape is identical to the keyword-only version, which is what makes
the before/after comparison meaningful.

Anchors are always included because introductions carry scope and conclusions
carry findings, both frequently relevant regardless of query. Note they are
*structural padding, not retrieval*: across the eval they account for 36 of 86
selected slots, so roughly a third of what reaches the model was not chosen by
relevance at all.

**Where vectors live.** `DocumentStore` persists them per row in
`content_embeddings_b64` (base64 float32, ~40 KB for 20 chunks; 30 KB raw) alongside
`embedding_model`. A document reloaded from history is queryable without
re-embedding. Vectors written by a different model are ignored, not compared.

**Loading.** Lazy, on first `encode()`. Import stays free — verified by a
subprocess test, because checking `sys.modules` in-process passes alone and
fails in a full run.

#### Measured retrieval accuracy

18 pairs across the fixtures, scored on whether the answering chunk was
**ranked** (strictly outscored every excluded chunk) rather than merely present.

| Method | ranked | PDF | Workbook |
|---|---|---|---|
| Keyword overlap, as originally shipped | 10/18 | 9/12 | 1/6 |
| Keyword overlap, tokenizer bug fixed | 13/18 | 9/12 | 4/6 |
| **Embeddings (current)** | **18/18** | **12/12** | **6/6** |

| Category | keyword (orig) | tokenizer-fixed | embeddings |
|---|---|---|---|
| `direct` | 4/4 | 4/4 | 4/4 |
| `vocab_overlap` | 4/6 | 6/6 | 6/6 |
| `cross_boundary` | 2/3 | 3/3 | 3/3 |
| `synonym` | 0/4 | 0/4 | **4/4** |
| `adversarial_sibling` | 0/1 | 0/1 | **1/1** |

**Attribution matters here.** Three of the eight gains over the original
baseline were a *tokenizer bug*, not the retrieval method: `_tokenize` matched
`[a-z]{3,}` and never saw `Q1` or `Q3`, so every quarterly sheet scored
identically and the selection was byte-identical no matter which quarter was
asked about. Fixing that regex alone takes keyword overlap from 10/18 to 13/18.
It has been fixed independently, since the fallback serves every query when the
model is missing.

The genuine embedding win is the **five cases no regex reaches** — four
`synonym` questions sharing no content word with their answer, plus the
adversarial sibling asking about "the second quarter" without writing `Q2`.

**Caveat on the score.** `ranked` requires strictly outscoring every excluded
chunk. Under integer keyword scores ties are common and that test does real
work; under cosine, exact ties are effectively impossible, so 18/18 is not
passing an identical bar. Margins are the honest substitute: smallest 0.0284,
median 0.2227, none below 0.02 — but the four narrowest are all near-identical
quarterly sheets (0.028–0.047), so that edge is thin and should be re-measured
after any model change.

**Context window management:**

```python
def _truncate_history(self, history):
    total = sum(len(h["content"]) // 4 for h in history)  # Approximate tokens
    if total <= MAX_HISTORY_TOKENS:
        return history
    # Always keep first 2 turns (contain document context)
    kept   = history[:2]
    budget = MAX_HISTORY_TOKENS - sum(len(h["content"]) // 4 for h in kept)
    for turn in reversed(history[2:]):    # Fill from most recent backward
        cost = len(turn["content"]) // 4
        if cost <= budget:
            kept.insert(2, turn)
            budget -= cost
    return kept
```

The first two turns always contain the system prompt and the initial document context. Dropping them would break the LLM's understanding of what document it's answering about. Subsequent turns are trimmed from oldest-first when the budget is tight — recent conversation is more relevant than old exchanges.


**Why JSON for Excel edits?** Excel files have strict tabular structure. If you ask the LLM to "return the modified spreadsheet as text," the output is a string representation that then has to be parsed back into Excel cells — with all the alignment ambiguity that entails. JSON operation lists are:
- **Deterministic**: `set_cell_value(row=5, col="B", value="150000")` is unambiguous
- **Auditable**: you can log exactly which cells were changed
- **Reversible**: you could implement undo by inverting the operations
- **Safe**: they fail explicitly if the referenced sheet/row/column doesn't exist

## 8. LLM Client — Groq Integration

**Location:** `utils/llm_client.py`

All LLM calls in every skill go through `LLMClient`. This centralises: API key management, multi-key round-robin, rate-limit retry, provider configuration, and the `available` guard that enables graceful degradation.

### Instantiation and Key Resolution

```python
client = LLMClient.from_config(cfg_dict)
```

`from_config` resolves API keys with this priority chain:
1. `GROQ_API_KEYS` environment variable (comma-separated for multiple keys)
2. `GROQ_API_KEY` environment variable (single key)
3. `groq.api_keys` from config dict
4. `groq.api_key` from config dict

**Why this chain?** Environment variables take precedence because they represent deployment-time secrets (set in the container/VM/Kubernetes secret). Config dict values are defaults for development. The comma-separated `GROQ_API_KEYS` enables multi-key rotation without any code changes — just set an environment variable with multiple keys.

### Multi-Key Round-Robin

```python
def chat(self, messages, temperature=None, max_tokens=3000):
    attempts = 0
    while attempts < len(self.api_keys):
        try:
            response = self._client.chat.completions.create(
                model=self.model,
                messages=messages,
                temperature=temperature or self.temperature,
                max_tokens=max_tokens,
                timeout=self.timeout,
            )
            return response.choices[0].message.content
        except openai.RateLimitError:
            attempts += 1
            self._current_key_idx = (self._current_key_idx + 1) % len(self.api_keys)
            self._client = None    # Force SDK re-initialisation with new key
            time.sleep(1)
    return None    # All keys exhausted — graceful None return
```

**Why `self._client = None` after key rotation?** The OpenAI SDK client is initialised with a specific API key at construction time. To switch keys, you must create a new client instance. Setting `_client = None` forces lazy re-creation on the next call via:

```python
@property
def _client(self):
    if self.__client is None:
        self.__client = openai.OpenAI(
            api_key=self.api_keys[self._current_key_idx],
            base_url=self.base_url,
        )
    return self.__client
```

### The `available` Guard

```python
@property
def available(self) -> bool:
    return len(self.api_keys) > 0
```

Every skill that uses the LLM checks `if not llm.available: return extractive_fallback()`. This single property is what makes the entire system work without an API key — every LLM-powered feature silently falls back to a rule-based or extractive implementation.

**Why check `len(api_keys) > 0` rather than actually testing the API?** A live API test at startup would add 1–3 seconds of latency, create a spurious API call in logs, and fail on network-restricted environments. Keys are validated syntactically (filtering out "PASTE_YOUR_GROQ_API_KEY_HERE" placeholder values) — this is sufficient to distinguish configured vs unconfigured deployments.

### Lazy Client Creation

The `openai.OpenAI` client is created on first use, not at `__init__`. This means `LLMClient` can be instantiated even before the `openai` package is confirmed available, without raising `ImportError` until an actual call is made. In test environments that mock `LLMClient`, the real `openai` import never happens.

## 9. Configuration System

**Location:** `utils/config.py`, `configs/default.yaml`

### Layered Resolution

```
configs/default.yaml  (checked-in defaults, safe for public repos)
    └── Environment variables override individual fields
        └── Typed Python dataclasses validate and expose values
```

### Why YAML + Dataclasses instead of Pydantic Settings?

Pydantic Settings (formerly `pydantic-settings`) is the modern standard for this pattern. The reason we use plain dataclasses: Pydantic Settings adds a mandatory second `pip install pydantic-settings` that many Python environments don't have by default. For a tool that should work with a single `pip install -r requirements.txt`, minimising surprising transitive dependencies reduces friction.

The trade-off: no runtime validation at config load time. We compensate with `AppConfig.validate()` which returns a list of human-readable issue strings that the Streamlit UI displays as warnings in the sidebar.

```python
if api_keys_env := os.environ.get("GROQ_API_KEYS") or os.environ.get("GROQ_API_KEY"):
```

## 10. File Handling & Validation

**Location:** `utils/file_handler.py`

### Path Traversal Prevention

```python
def save_upload(file_bytes: bytes, original_name: str, tmp_dir: str) -> Path:
    safe_name = Path(original_name).name    # Strips all directory components
    # "../../etc/passwd" → "passwd"
    # "../../../root/.bashrc" → ".bashrc"
    file_path = Path(tmp_dir) / safe_name
    ...
```

This is not a hypothetical vulnerability. Streamlit's file uploader passes the `name` attribute from the browser's `File` object. A malicious upload with `name="../../etc/cron.d/malware"` would write to a system path without this protection. `Path(name).name` extracts only the base filename, making path traversal structurally impossible.

### Temporary File Lifecycle

```python
tmp_dir = make_temp_dir()     # mkdtemp() → /tmp/docagent_XXXXXX/
try:
    file_path = save_upload(bytes, name, tmp_dir)
    result = agent.run(file_path)
finally:
    cleanup_temp_dir(tmp_dir)    # shutil.rmtree — always runs, even on exception
```

`finally:` is not optional. Without it, exception paths (pipeline crash, network timeout) leave orphaned temp files. On a server processing many documents per hour, this leaks disk space steadily. The `finally:` block guarantees cleanup regardless of execution path.

## 12. UI Layer — Streamlit

**Location:** `ui/app.py`, `ui/components/results_view.py`, `ui/styles/custom.css`

### 12.1 Why Streamlit

**The alternative stack** would be: FastAPI backend + React/Next.js frontend + a build pipeline. This is the right choice for a team-scale product with multiple developers. For a single-developer AI tool, it would mean:
- ~2,000 lines of TypeScript to replicate what Streamlit provides in ~300 lines of Python
- A separate build process, node_modules, webpack config
- CORS configuration between the FastAPI backend and the frontend
- A deployment strategy that handles two separate services

Streamlit collapses this to one Python file. The cost: limited layout control, no WebSocket-native bidirectional communication, all UI state is string/number/bool. The benefit: the entire UI can be read, understood, and modified in an afternoon.

**Key Streamlit constraint:** Streamlit re-runs the **entire** `main()` function from top to bottom on every user interaction (button click, file upload, slider change). State that needs to persist across reruns must be stored explicitly in `st.session_state`. Understanding this re-run model is the prerequisite for understanding all architectural decisions in the UI.

### 12.2 Session State Architecture

```python
# File data persists across theme toggles, tab switches, button clicks
st.session_state["_file_data"] = [{"name": "report.pdf", "bytes": b"..."}]

# Pipeline results indexed by filename — survive any rerun
st.session_state[f"doc_result_{filename}"] = result

# ParsedDocument stored separately — needed for Chat and Edit tabs
st.session_state[f"parsed_doc_{filename}"] = result.parsed_document

# TTS audio cache — avoid regenerating on every rerun (if server-side TTS used)
st.session_state[f"tts_audio_{filename}"] = (audio_bytes, mime_type)
```

**Why store file bytes in session state?** Streamlit's `st.file_uploader` returns `UploadedFile` objects that are only valid within the current script execution. If the user toggles the theme (a non-upload interaction), `uploaded_files` becomes an empty list on the next rerun even though no new upload happened. Storing bytes in session state at upload time makes files persistent until the user explicitly clears them.

**The `@st.cache_resource` / monkey-patch problem:**

`DocumentAgent` is cached across reruns:

```python
@st.cache_resource(show_spinner=False)
def _get_agent(summary_length="Standard", summary_tone="Professional"):
    return DocumentAgent(config=...)
```

The pipeline patches `agent._log_step` to update a progress bar during processing:

```python
_orig_log = agent._log_step
while hasattr(_orig_log, "__wrapped_orig__"):
    _orig_log = _orig_log.__wrapped_orig__    # Unwrap previous patches

def _progress_log_step(skill_name, success, duration_ms, error=None):
    _orig_log(skill_name, ...)    # Call the true original
    bar.progress(pct, text=label)

_progress_log_step.__wrapped_orig__ = _orig_log    # Tag for future unwrapping
agent._log_step = _progress_log_step
```

The problem: on a second analysis with the same settings (cache hit), the agent is the same Python object. If we just do `agent._log_step = new_closure`, the previous patch is now "the original" from `_progress_log_step`'s perspective. That previous closure holds a reference to a now-dead Streamlit progress bar widget. Calling it raises an exception.

The `__wrapped_orig__` chain-unwrapping pattern solves this: always traverse to the *real* original method before patching, regardless of how many patches have accumulated. The `finally:` block always restores the real original, so the cache stays clean between analyses.

### 12.3 Theme System

DocAgent supports dark and light themes toggled by the sidebar button. The implementation uses CSS custom properties (variables) injected by `st.markdown(unsafe_allow_html=True)`:

**Dark mode (default):** Defined in `ui/styles/custom.css` with variables like `--bg-base: #0f0e1a`, `--accent: #7C3AED`.

**Light mode:** Defined in `_LIGHT_VARS` (inline in `app.py`) as a CSS override block that redefines the same variables: `--bg-base: #fafafa`, `--accent: #1D4ED8`.

```python
def _inject_css() -> None:
    css_path = Path(__file__).parent / "styles" / "custom.css"
    if css_path.exists():
        with open(css_path) as fh:
            st.markdown(f"<style>{fh.read()}</style>", unsafe_allow_html=True)

    if st.session_state.get("theme") == "light":
        st.markdown(_LIGHT_VARS, unsafe_allow_html=True)   # Override CSS variables
```

**Why CSS variables instead of two separate CSS files?** Every component uses variables like `var(--bg-card)` and `var(--accent)`. Switching themes is one `st.markdown` call that redefines 20 variables. If we had two separate files, we'd need to conditionally apply different class names to every component — multiplying the maintenance burden by 2× across every style rule.

**Why Streamlit doesn't natively support this:** Streamlit has its own theming system (`[theme]` in `.streamlit/config.toml`) but it only controls base colours and fonts. Custom component backgrounds, glassmorphic effects, badge colours, and animation styles require direct CSS injection.

### 12.4 Layout & Full-Width Rendering

A non-obvious bug exists in early versions: results rendered in a narrow column after clicking "Analyze" even though the app uses `layout="wide"`.

**Root cause:** The "Analyze" button is displayed in a centered column for visual polish:

```python
btn_col = st.columns([1, 2, 1])[1]
with btn_col:
    if st.button("Analyze", ...):
        for fd in pending:
            _run_pipeline(fd["name"], fd, overrides)   # ← BUG: inside column context!
```

When `_run_pipeline` is called inside `with btn_col:`, all its output — including the entire `render_results` call — is rendered inside the center column. Streamlit's layout model confines all `st.*` calls made within a `with col:` block to that column's width.

**Fix:** Separate the button click detection from the pipeline execution:

```python
btn_col = st.columns([1, 2, 1])[1]
with btn_col:
    do_analyze = st.button("Analyze", ...)   # Only the button widget is in the column

if do_analyze:    # Pipeline runs at top level — full width
    for fd in pending:
        _run_pipeline(fd["name"], fd, overrides)
```

The button's visual centering is preserved; the results have full width.

On subsequent reruns (after any rerun-triggering interaction like clicking a download button), the file has moved from `pending` to `processed`, so `_run_pipeline` is called from the top-level `for fd in processed:` loop — correctly at full width. This is why the bug only manifests on the initial analysis render, not on subsequent reruns.

### 12.5 Read-Aloud / TTS Feature

The read-aloud feature lets users listen to a document's summary via the browser's built-in speech synthesis engine. The implementation lives in `ui/components/results_view.py`.

#### Why the Browser's Web Speech API, Not Server-Side TTS

Options considered:

| Approach | Quality | Dependencies | Latency |
|---|---|---|---|
| Browser Web Speech API | Good (neural voices on Chrome/Safari) | None | Instant |
| `gTTS` (Google TTS) | Excellent | `gtts`, internet | 3–5s generation |
| `kokoro` Python package | Excellent (open-source neural) | `kokoro`, `espeak-ng`, ~1GB | 5–15s first run |
| `pyttsx3` | Poor (robotic system voices) | `pyttsx3`, OS voices | Instant |

The Web Speech API was chosen because:
1. **Zero dependencies** — no `pip install`, no system binaries, no API keys
2. **Neural quality on modern browsers** — Chrome's Google US English, Safari's Siri voices are neural TTS models comparable to cloud TTS APIs
3. **Zero latency** — speech starts instantly; no generation step
4. **Client-side** — audio never leaves the user's device, no privacy concerns

The trade-off: quality varies by browser and OS. On Chrome with Google US English, quality is excellent. On Firefox with system voices, it's acceptable. The generation counter pattern ensures reliability across all browsers.

#### How It Works: `streamlit.components.v1.html`

Streamlit's `st.markdown(unsafe_allow_html=True)` renders HTML but **strips `<script>` tags**. To run JavaScript, we use `components.html()`:

```python
components.html(f"""
<!DOCTYPE html>
<html>
<body>
  <button onclick="toggleSpeech()">🔊</button>
  <script>
    const _segments = {tts_segments_json};
    // ... speech synthesis logic
  </script>
</body>
</html>
""", height=165)
```

`components.html()` renders the HTML in a sandboxed `<iframe>` in the Streamlit app. The Web Speech API is available in iframes in all major browsers (Chrome, Safari, Firefox, Edge) without additional iframe permissions.

**Why an iframe?** Streamlit's component model requires custom HTML to run in iframes so Streamlit can manage the component lifecycle, prevent CSS leakage, and communicate via postMessage if needed. The downside: the TTS component is visually isolated from the Streamlit theme. We compensate with transparent backgrounds and CSS that mimics the app's colour palette.

#### Text Preprocessing: `_prepare_tts_segments()`

The raw summary contains Markdown syntax that would be read aloud literally ("hashtag hashtag Introduction", "asterisk asterisk key finding asterisk asterisk"). The `_prepare_tts_segments()` function converts it to typed segments:

```python
def _prepare_tts_segments(summary: str) -> list[dict]:
    # 1. Strip source citations: [Source: Pages 1-3] → ""
    text = re.sub(r'\[Source:[^\]]*\]', '', summary)
    # 2. Strip inline code
    text = re.sub(r'`[^`]*`', '', text)
    # 3. Unwrap markdown links: [label](url) → label
    text = re.sub(r'\[([^\]]*)\]\([^\)]*\)', r'\1', text)
    # 4. Strip numbered citations: [1], [2] → ""
    text = re.sub(r'\[\d+\]', '', text)

    segments = []
    for line in text.split('\n'):
        s = line.strip()
        if not s:
            continue
        # Classify line type for voice modulation
        if re.match(r'^#{1,2}\s', s):
            seg_type, s = 'heading',    re.sub(r'^#{1,2}\s+', '', s)
        elif re.match(r'^#{3,6}\s', s):
            seg_type, s = 'subheading', re.sub(r'^#{3,6}\s+', '', s)
        elif re.match(r'^[•◆◇▪▸→◈\-\*]\s', s):
            seg_type, s = 'bullet',     re.sub(r'^[•◆◇▪▸→◈\-\*]\s+', '', s)
        elif re.match(r'^\d+\.\s', s):
            seg_type, s = 'numbered',   re.sub(r'^\d+\.\s+', '', s)
        else:
            seg_type    = 'body'
        # Strip remaining Markdown bold/italic/strikethrough
        s = re.sub(r'\*{1,3}(.*?)\*{1,3}', r'\1', s)
        s = re.sub(r'_{1,2}(.*?)_{1,2}',   r'\1', s)
        s = re.sub(r'[~>]', '', s).strip()
        if s:
            segments.append({'text': s, 'type': seg_type})
    return segments
```

**Why classify segments by type?** The JavaScript speech engine applies different `rate` and `pitch` per segment type:

| Segment type | Rate (at 1.0× speed) | Pitch | Effect |
|---|---|---|---|
| `heading` | 0.82 | 1.18 | Slower, higher — signals a section change |
| `subheading` | 0.86 | 1.10 | Slightly slower, mild rise |
| `bullet` / `numbered` | 0.90 | 0.97 | Slightly lower — signals list items |
| `body` | 0.92 | 1.00 | Natural, conversational baseline |

The result sounds like a human reader who naturally slows down and raises pitch when announcing a new section, and drops into a reading cadence for bullet points.

#### Voice Selection Strategy

```javascript
function _pickVoice() {
    const voices = window.speechSynthesis.getVoices();
    // Priority 1: Named high-quality voices
    const named = ['Google US English', 'Google UK English Female',
        'Microsoft Aria Online (Natural)', 'Samantha', 'Karen', 'Daniel', ...];
    for (const n of named) {
        const v = voices.find(v => v.name === n);
        if (v) return v;
    }
    // Priority 2: Any en voice with quality keywords in the name
    const hi = voices.filter(v =>
        v.lang.startsWith('en') &&
        /(neural|online|enhanced|premium|natural)/i.test(v.name));
    if (hi.length) return hi[0];
    // Priority 3: Any Google en voice (cloud-backed, neural quality)
    const goog = voices.filter(v => v.lang.startsWith('en') && /google/i.test(v.name));
    if (goog.length) return goog[0];
    // Fallback: any en-US, then any English
    return voices.find(v => v.lang === 'en-US') || voices.find(v => v.lang.startsWith('en'));
}
```

**Why voice selection matters:** `window.speechSynthesis.getVoices()` returns different voices on every browser/OS combination. Chrome on macOS may have 50+ voices including Google's neural cloud voices. Firefox on Linux may have only the system's eSpeak voices. The priority list selects the highest-quality available voice without knowing the runtime environment.

**The `onvoiceschanged` callback:**

```javascript
speechSynthesis.onvoiceschanged = () => { _voice = null; };
```

Browsers load voices asynchronously on some platforms (particularly Chrome on macOS). `getVoices()` returns an empty array immediately after page load and populates after a short delay. Setting `_voice = null` on the `onvoiceschanged` event forces re-selection on the next `_next()` call, ensuring the best voice is used rather than a placeholder.

#### The Generation Counter Pattern (Speed-Change Bug Fix)

The speed control slider lets users change playback speed mid-reading. The naive implementation (`cancel()` + rebuild queue + `_next()`) fails because `cancel()` fires an `onerror` event on the current utterance *asynchronously*. That `onerror` handler calls `_reset()`, which wipes `_speaking = false`, `_idx = 0`, `_queue = []` — nullifying the resume state we just set up.

The generation counter pattern solves this:

```javascript
let _gen = 0;   // Incremented on every intentional cancel

function _makeUtterance(text, segType, gen) {
    const u = new SpeechSynthesisUtterance(text);
    // ...rate/pitch/vol setup...

    // Capture gen in closure — if _gen changes before this fires, ignore it
    u.onboundary = (e) => { if (_gen === gen) _charOffset = e.charIndex; };
    u.onend      = ()  => { if (_gen === gen) { _charOffset = 0; _next(gen); } };
    u.onerror    = (e) => { if (_gen === gen && e.error !== 'canceled') _reset(); };
    return u;
}
```

When `_applySpeed()` changes the speed:

```javascript
function _applySpeed(stepIdx) {
    // ... update _speedMult, UI display, slider position ...

    if (_speaking) {
        const currentSegIdx = Math.max(0, _idx - 1);
        const remaining = _segments[currentSegIdx].text.slice(_charOffset).trim();

        _gen++;    // Invalidate all callbacks from the current utterance
        window.speechSynthesis.cancel();

        _charOffset = 0;
        _idx        = currentSegIdx;
        _resumeText = remaining || null;   // null = use full segment text
        _next(_gen);    // Start immediately with new speed
    }
}
```

`_gen++` before `cancel()` means: any `onerror` or `onend` that fires after this point will see `_gen !== gen` (their captured closure value) and will be silently discarded. The new `_next(_gen)` call runs with the bumped generation and sets up fresh callbacks with the new `gen` value.

#### Character-Level Resume: `onboundary`

When speed changes mid-sentence, we want to resume from the current word, not the start of the segment (paragraph). The `onboundary` event fires at every word and sentence boundary:

```javascript
u.onboundary = (e) => {
    if (_gen === gen) _charOffset = e.charIndex;
    // e.charIndex = index of the first character of the UPCOMING word
};
```

`_charOffset` tracks the position of the last word boundary within the current utterance's text. When resuming:

```javascript
const remaining = _segments[currentSegIdx].text.slice(_charOffset).trim();
_resumeText = remaining;
```

`slice(_charOffset)` gives us everything from the last word boundary to the end — at most, the current word is repeated once (we rewind to the start of the word being spoken), then speech continues from there with the new speed.

**Browser support:** `onboundary` is well-supported in Chrome and Safari. Firefox has historically had inconsistent support. In Firefox, `_charOffset` may stay at 0, causing the segment to restart from the beginning on speed change — a graceful degradation (starts from sentence start, not word start) rather than a crash.

## 14. Testing Strategy

**Location:** `tests/test_skills.py`, `tests/test_agent.py`

### Core Principles

1. **No real files** — Tests use in-memory text fixtures, not actual PDFs. Reason: PDFs are binary blobs; keeping them in the repo adds version control noise and makes tests brittle to changes in external tools (pdfplumber updates that change whitespace extraction).
2. **No network calls** — All LLM calls are mocked. Tests should run with no internet connection, no API key, and complete in under 30 seconds.
3. **Fixture helpers** — `_make_parsed_doc(text, file_type, n_pages)` creates a `ParsedDocument` from plain text. All skills that need a `ParsedDocument` use this helper.
4. **Skill isolation** — Each skill is instantiated with `config={}` and tested independently. A failing classifier test tells you the classifier is broken, not the pipeline.

### Key Test Fixtures

```python
NORMAL_TEXT = """Annual Report 2024.

Revenue grew 15% year-over-year to $4.2 billion.
Operating margin improved from 18.3% to 21.1%.
The Board recommends a final dividend of $0.85 per share."""

QUESTIONNAIRE_TEXT = """Customer Satisfaction Survey

Q1. How satisfied are you with our service overall?
    [ ] Very satisfied  [ ] Satisfied  [ ] Neutral  [ ] Dissatisfied

2. On a scale of 1-5, please rate our response time:
   1 □  2 □  3 □  4 □  5 □

Please describe any issues you experienced: _______________

I consent to being contacted for follow-up: Yes □  No □"""
```

The questionnaire text deliberately includes multiple signal types (Q-numbering, checkbox items, Likert-style prompts, fill-in-blank, consent language) to test the classifier's combined scoring, not just pattern matching.

### SkillRegistry Isolation in Tests

```python
def setUp(self):
    SkillRegistry().reset()    # Clear singleton between tests
```

Without `reset()`, skills registered by one test contaminate the next test's registry state. Always call `reset()` in `setUp` for tests that touch the registry.

## 15. Common Extension Patterns

### Add a New Input Format

1. Create `skills/my_reader_skill.py` → inherits `BaseSkill`, returns `ParsedDocument(file_type="mytype", ...)`
2. Add to `SUPPORTED_EXTENSIONS` in `agents/document_agent.py`: `{".myext": "mytype"}`
3. Add to `ALLOWED_EXTENSIONS` in `utils/file_handler.py`
4. Add to `st.file_uploader(type=[...])` in `ui/app.py`
5. Add routing in `DocumentAgent._select_reader()`: `elif file_type == "mytype": return self._my_reader`

That's the complete blast radius — 4 lines across 3 files.

### Add a New Processing Step

1. Create `skills/my_step_skill.py` with `execute(SkillInput) → SkillOutput`
2. Add `self._my_step = MyStepSkill(config=...)` to `DocumentAgent.__init__`
3. Add the call in `DocumentAgent._run_core_pipeline()` at the appropriate point
4. If the result should be surfaced to users: add a field to `PipelineResult` in `core/pipeline_result.py`

If the step should be planner-gated (only run for certain document types/domains), add a flag to `PipelineFlags` in `agents/planner.py` and the condition in `PipelinePlanner.plan()`.

### Add a New LLM-Powered Feature

The standard pattern used by all existing LLM skills:

```python
from utils.llm_client import LLMClient

class MyLLMSkill(BaseSkill):
    name = "my_llm_skill"
    required_inputs = ["text"]

    def execute(self, inputs: SkillInput) -> SkillOutput:
        llm = LLMClient.from_config(self.config)
        if not llm.available:
            # Always have a non-LLM fallback
            return self._extractive_fallback(inputs)

        response = llm.chat([
            {"role": "system", "content": "You are a {domain} analyst..."},
            {"role": "user",   "content": inputs.data["text"][:4000]},
        ], temperature=0.1, max_tokens=1000)

        if response is None:
            return self._extractive_fallback(inputs)

        return SkillOutput(success=True, data={"result": response})
```

Critical: always implement a non-LLM fallback. `llm.chat()` returns `None` when all API keys are rate-limited or unavailable. Skills that return `SkillOutput(success=False, ...)` on LLM unavailability degrade gracefully; skills that crash when `response is None` break the pipeline.

### Extend the UI with a New Tab

Results are displayed in `render_results()` in `ui/components/results_view.py`. The tab list is:

```python
tab_labels = ["Summary", "Questions", "Chat", "Edit"]
tabs = st.tabs(tab_labels)

with tabs[0]:
    # Summary content
with tabs[1]:
    # Questions content
# ... etc
```

To add a tab:
1. Add its label to `tab_labels`
2. Add a `with tabs[n]:` block with the content
3. If the tab has complex logic, extract it to a `_render_my_tab(result, fname)` function following the existing pattern

## 16. Known Gotchas & Production Notes

### ffmpeg Must Be a System Binary

`pydub` and `yt-dlp` both call `ffmpeg` as an external process. The Python packages `ffmpeg-python` and `yt-dlp` provide Python wrappers but they do nothing without the underlying `ffmpeg` binary installed on the system.

```bash
ffmpeg -version        # Should show version info
which yt-dlp           # Should show a path
```

If `ffmpeg` is missing, audio uploads and YouTube processing silently fail with "No such file or directory" deep in the subprocess call stack.

### Groq's 25 MB Whisper File Size Limit

Audio downloaded as WAV is uncompressed: 5 minutes ≈ 50 MB. MP3 at 128 kbps = ~5 MB. Never change the audio download format from MP3 to WAV or FLAC — anything longer than ~2 minutes will hit Groq's 25 MB limit and return a 413 error.

### PaddleOCR First-Run Model Download

`PPStructureV3` downloads ~400 MB of model weights from Baidu's CDN on first use. In a container with restricted internet access (or air-gapped), this fails silently (returns empty tables, not an error). Pre-download models and mount them at PaddleOCR's expected path, or set `PADDLE_MODEL_DIR` to point to a local cache.

### `@st.cache_resource` and Monkey-Patching

The `agent._log_step` monkey-patch for progress bar updates **must** be restored in a `finally` block. If code is added between `agent.run()` and the `finally:` block that raises an exception, the patch leaks and the next analysis fails with a stale widget reference.

The `__wrapped_orig__` chain-unwrapping is also load-bearing. If you add another place in the code that patches `agent._log_step`, you must also implement the chain-unwrapping pattern, otherwise it accumulates infinite closures.

### SkillRegistry Singleton in Tests

`SkillRegistry` is a module-level singleton. One test that monkey-patches a skill will corrupt subsequent tests. Always call `SkillRegistry().reset()` in `setUp()` for test classes that modify the registry.

### Placeholder API Keys in Config

`configs/default.yaml` ships with `api_key: "PASTE_YOUR_GROQ_API_KEY_HERE"` and
`api_keys: "PASTE_MULTIPLE_GROQ_API_KEYS_HERE"`.

> **Corrected.** This section previously claimed `LLMClient` filtered the
> placeholder out, and showed a line of code to that effect. That code did not
> exist anywhere in the codebase. The placeholder *was* returned as a live key —
> verifiably position 2 of 9 on a machine with 8 real keys configured — and was
> sent to the Groq API, guaranteeing a 401 and consuming a rotation slot on
> every rate-limit failover.

Filtering now happens in `resolve_groq_api_keys()` in `utils/config.py`, which is
the single resolution point every caller uses (`DocumentAgent.__init__`,
`LLMClient.from_config`, and `AppConfig.validate`). A candidate is rejected when
it:

- contains a placeholder marker (`PASTE`, `REPLACE_ME`, `YOUR_`, `_HERE`,
  `CHANGE_ME`, `DUMMY`, matched case-insensitively), or
- is shorter than 20 characters (a real Groq key is 56), or
- contains whitespace.

Rejections are logged at WARNING with the reason and the character count, but
never the value — a rejected candidate may still be a real secret.

**Known residual gap.** `AudioReaderSkill._transcribe_audio()` does *not* route
through `resolve_groq_api_keys()`. It resolves keys itself:

```python
raw_keys = (os.environ.get("GROQ_API_KEYS") or os.environ.get("GROQ_API_KEY")
            or self._groq_cfg.get("api_keys", "") or self._groq_cfg.get("api_key", ""))
```

In the production path this is safe: `DocumentAgent.__init__` builds the skill's
config from `resolve_groq_api_keys()`, so the keys it receives are already
filtered. The placeholder can only reach it if the skill is instantiated
directly with the raw YAML config *and* neither env var is set — e.g. in a test
or script on a machine with no `.env`. Consolidating every LLM call site onto one
shared client is tracked separately; until then, prefer building skills through
`DocumentAgent` rather than instantiating them with raw config.

If `available` returns `False` unexpectedly, check the logs for
"Ignoring Groq API key candidate" — that names the reason.

### The Full-Width Layout Rule

Any `st.*` call made inside a `with col:` block is confined to that column's width. This includes calls made inside functions called from within the block. If you add new content that should be full-width (a new results section, a new tab, an export button), ensure it is not called from within any `with st.columns():` context — even transitively through a function call.

### Large Document Performance Expectations

| Document | Parse | Structure Rec. | Summarise | Total |
|---|---|---|---|---|
| 10-page PDF, text only | 2–5s | (skipped) | 5–15s | ~20s |
| 50-page technical PDF | 15–30s | 2–5 min (CPU) | 30–90s | 3–5 min |
| 200-page financial report | 30–60s | 5–15 min (CPU) | 2–10 min | 8–25 min |
| 5-minute audio / YouTube | 15–30s (download) + 5–10s (transcribe) | (skipped) | 5–15s | ~1 min |

Structure recognition on CPU is the bottleneck for technical/financial PDFs. If processing speed is critical, either: (a) deploy with a GPU and set `use_gpu=True` in config (10–15× speedup), or (b) disable structure recognition for domains where tables are not critical (`TARGET_DOMAINS` in `StructureRecognitionSkill`).
